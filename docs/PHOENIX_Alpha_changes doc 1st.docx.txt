Consolidated Click-dummy User-Flow &amp; Build-Freeze Review
Role requirements, onboarding routes, menu logic, collaboration spaces, profile evolution and Alpha-safe matchmaking

1. Executive view
This report consolidates the current Alpha FRD, WSS clarification decisions, the 9 October wireframe meeting, the live clickdummy review evidence, the build-freeze review and the Shaligram implementation action report. It does not repeat every screen. Instead, it asks one practical question for each role and screen family: does the clickdummy help this user do what the Alpha says they should be able to do, with the correct permissions, privacy, human review and next action?
Simple rule for the next iteration
Design the platform around the user’s current role, context, purpose and next useful action - not around exposing every module. The same underlying services can remain reusable, but each user should see only the work, decisions and records relevant to them.

Implement safe role transitions
Observed failure. Samuel switched from Mentor in Excelsior to Participant in Riverside. A notification still opened Excelsior Mentor Requests with Accept and Decline controls under the Riverside Participant view. No action was submitted. This is a demonstrated route and control exposure; backend execution authority remains to be tested.
Required transition behavior
1. Provide a persistent header switcher listing each active role and its organisation or programme context. Use the invited context on first login and the last-used valid context afterwards. Pending or inactive assignments must not be selectable for work.
2. On selection, re-evaluate the assignment and its validity. Save or prompt for an authorised unsaved draft before leaving. Never attach a draft from one context to an object in another.
3. Rebuild the dashboard, navigation, review queue, requests, counts, search and object access for the new context. Close dialogs and invalidate stale action controls and cached object content.
4. Recheck the destination on every notification and deep link. A permitted cross-context notice must name its context and require a safe switch to the correct active assignment before opening protected content or executing an action.
5. Handle a revoked role, expired mandate, missing membership or changed consent without displaying protected content. Offer a valid context or a clear recovery route. Suspension in one organisation must leave other authorised contexts and the person’s identity available.

5.1 Matchmaking logic Shaligram can build now
The Match Brief should show why a connection is being suggested, what information supports it, what is missing and what human action comes next. Matching may combine positive fit with governance/readiness gates; it should not hide behind a single number.
Positive-fit dimensions
Governance / readiness checks
Never use as hidden matching factors
Goal/purpose; need-offer complementarity; skills/capabilities; learning interest; availability; location/context; language/preferences; sector/project relevance; resources; role/affiliation.
Matching consent; field visibility; context eligibility; valid role/mandate; opportunity state/expiry; prerequisites; restrictions; availability; unresolved safety/governance flags.
Personality or psychological state; religion/political belief; health; deservingness; moral worth; trustworthiness; universal synergy/coherence score.
Recommended Match Brief layout: Why suggested -&gt; source fields -&gt; missing information -&gt; readiness gaps -&gt; uncertainty -&gt; permission/authority status -&gt; restrictions -&gt; recommended next human action -&gt; “Do not introduce yet” reason where applicable.
5.2 Matchmaking in plain language
Shaligram does not need a complex scoring engine to demonstrate useful matching in Alpha. A simple governed sequence is enough:
Step
System behavior
1
Use only fields the person has allowed for matching in the active context.
2
Find possible complementarity across purpose/goal, need-offer, skills, learning interest, availability, language, location/context and resources.
3
Apply readiness gates: valid role/mandate, visibility, opportunity state, prerequisites, restrictions and safety/governance flags.
4
Create a Match Brief that explains why the match is suggested, what is uncertain and what is missing.
5
Human steward reviews a PHOENIX-generated match. Direct authorized collaboration may bypass the Match Brief route but not permission/consent checks.

Both parties consent before contact details are disclosed.
7
After introduction: Close / Continue Conversation / Link Existing Workspace / Create New Workspace.
Example: a student who has shared an interest in climate-resilient cities and three hours/week availability may be suggested for a partner's urban-heat mapping opportunity because the need, capability, time and context fit. The Match Brief must still show the source fields, gaps and consent status; it must not infer personality or trustworthiness.

DECIDE
8. Screenshot evidence: what to keep and what to correct

Consent screen: useful clause comparison, but the live v3 wording bundled optional purposes and removed withdrawal choices. Correct by restoring separate purpose consent and preserving rights access even when re-acceptance is pending.

Participant pathway: the visual progress model is useful. Add step type, prerequisite/dependency, participant acceptance, optional/conditional handling, Satisfied by Prior Evidence and Blocked reasons so the UI matches FR-F04.

Circle voting: the current “weighted votes” screen conflicts with the Alpha decision. Replace owner double weight with one eligible member = one vote; show threshold, quorum/window and denominator separately.

Evidence screen: record metadata and history are useful. Keep review status, E-level, confidentiality, lifecycle and release as separate fields; “Restricted” must not be a review outcome.

Sponsor dashboard: visual reporting is promising, but project pitches and staged tranches exceed Alpha. Reframe around seat utilisation, approved initiatives, aggregate progress, approved evidence and funder-safe reports.

Appendix B. Alpha-safe design language for Shaligram
Use “My Purpose / Current Direction” rather than a purpose score or “alignment score”.
Use “Why suggested” and “What is missing” in Match Briefs rather than a single match score.
Use “Recommended next action” only when it is clear who recommended it and whether the participant must accept it.
Use “Threaded discussion” rather than “real-time chat” unless WSS explicitly changes scope.
Use “Action Workspace” as the canonical system concept; packs may display Action Room / Coherence Cell / Project Room.
Use “Approved evidence summary” and “funder-safe Harvest” for sponsor reporting; avoid implying ownership of participant data.
Use “participant-reported” or “activity-derived support indicator”; avoid well-being, personality, readiness or trustworthiness inference.
Use “AI draft / advisory” with sources and uncertainty; never “AI approved”, “AI rejected” or “AI decided”.
